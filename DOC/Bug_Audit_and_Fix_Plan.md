## 1. Klasifikasi Tingkat Keparahan (Severity Level Scale)
* 🔴 **CRITICAL (P1)**: Bug yang menyebabkan kehilangan dana, kegagalan rekonsiliasi, memory leak, atau kerentanan bypass autentikasi.
* 🟡 **MAJOR (P2)**: Anomali UX, timeout jaringan tanpa retry, overflow layout pada layar tertentu, atau desinkronisasi status.
* 🟢 **MINOR (P3)**: Ketidakkonsistenan penamaan, dead code, atau optimasi bundle/file size.

| **BUG-012** | Merchant Dashboard API Sync | Halaman No-Code Payment Links (`payment-links/page.tsx`) awalnya hanya mengupdate state in-memory lokal tanpa sinkronisasi live ke endpoint backend `GET /api/v1/payment-links`, `POST /api/v1/payment-links`, dan `PATCH /api/v1/payment-links/:id/toggle`. | 🟡 MAJOR | ✅ Fixed | Diintegrasikan API call asinkronus dengan token autentikasi merchant, status loading `isCreating` untuk mencegah double-click, serta fallback optimistik jika backend offline. Modal pembuatan diekstrak ke `CreatePaymentLinkModal.tsx` agar ukuran file tetap <= 400 baris. |
| **BUG-013** | Frontend Bundle Hygiene | Import `useEffect` tidak terpakai pada `admin/src/components/ui/Tooltip.tsx`. | 🟢 MINOR | ✅ Fixed | Unused import dihapus; `tsc --noEmit` diverifikasi bersih tanpa peringatan. |
| **BUG-014** | EVM Watcher (BSC/POLYGON) | Pemindaian `eth_getLogs` tanpa filter topic target address (`topics[2]`) menyebabkan RPC Mainnet melempar error *10,000 log overflow* atau HTTP 429 karena volume transfer USDT publik. Selain itu, pemindaian pada tip rantai (`currentBlock`) tanpa *confirmation lag* rentan terhadap *micro-reorg double-spend attacks*. | 🔴 CRITICAL | ✅ Fixed | Diterapkan *targeted address filtering* via `topics: []any{EVM_TRANSFER_TOPIC, nil, addressTopics}` (format 32-byte hex zero-padded), membatasi log hanya pada deposit address aktif. Diterapkan *confirmation lag depth* (default 3 blok untuk BSC, 15 blok untuk Polygon) via `safeHead := currentBlock - w.requiredConfs` untuk memitigasi risiko reorg. Dilengkapi unit test komprehensif pada `evm_watcher_test.go`. |
| **BUG-015** | Database Engine (SQLite) | Mode SQLite default (Rollback Journal) memblokir operasi pembacaan saat penulisan berlangsung, memicu error `database is locked (5)` saat 4 watcher paralel, background pruner, dan request HTTP aktif bersamaan. | 🔴 CRITICAL | ✅ Fixed | Diaktifkan SQLite Write-Ahead Logging (`PRAGMA journal_mode=WAL;`), waktu tunggu konkurensi (`PRAGMA busy_timeout=5000;`), serta checkpoint sinkronisasi (`PRAGMA synchronous=NORMAL;`). Kolam koneksi diatur optimal (`MaxOpenConns=25`, `MaxIdleConns=5`). |
| **BUG-016** | API Security & Rate Limit | Endpoint publik autentikasi (`/auth/login`, `/auth/register`) dan pembuatan invoice (`/invoices`, `/pay/:slug/invoice`) belum memiliki pembatasan laju request (rate limit), rentan terhadap serangan *credential stuffing* dan DoS invoice flooding. | 🟡 MAJOR | ✅ Fixed | Diimplementasikan thread-safe sliding-window / token-bucket IP Rate Limiting middleware (`rate_limit_middleware.go`) dengan auto-purge memory IP usang setiap 5 menit. Membatasi auth ke 15 req/menit dan public invoice ke 60 req/menit, dilengkapi header `Retry-After: 60` saat batas terlampaui. Dilengkapi unit test `TestRateLimitMiddleware_BlocksExcessiveRequests`. |
| **BUG-017** | Sentinel Anti-Tamper & DRM | Klien dapat membypass remote kill-switch lisensi selamanya dengan cara mem-blackhole domain server lisensi di `/etc/hosts` atau firewall, karena kegagalan HTTP heartbeat hanya menghasilkan warning tanpa batasan waktu offline. | 🔴 CRITICAL | ✅ Fixed | Diterapkan batas ketat **72-Hour Maximum Offline Grace Period** (`maxOfflineGrace = 72 * time.Hour`). Jika gateway gagal terhubung ke heartbeat server dalam 72 jam, status lisensi otomatis dikunci menjadi `REVOKED` pada `IsOperational()` dan `checkRemoteHeartbeat()`, menghentikan seluruh operasi gateway. Dilengkapi unit test `TestManager_OfflineGracePeriod`. |
| **BUG-018** | Webhook Engine & Idempotency | Pengiriman webhook callback ke endpoint merchant tidak menyertakan ID pengiriman unik atau idempotency key, menyulitkan backend merchant melakukan deduplikasi transaksi jika terjadi *network retry*. | 🟡 MAJOR | ✅ Fixed | Setiap pengiriman webhook (otomatis maupun manual test/replay) diinjeksi header `X-13C-Delivery-ID: del_xxx` dan `Idempotency-Key: del_xxx` secara deterministik dan unik via `uuid.New().String()[:12]`. Header ini juga dipetakan ke dalam `ReplayResult` untuk kemudahan audit log. Dilengkapi unit test `TestDispatchSync_InjectsIdempotencyAndDeliveryHeaders`. |
| **BUG-019** | Sweeper Engine (Dust & Gas) | Ephemeral deposit addresses dengan saldo kecil (*dust* < 1 USDT atau < biaya gas) disapu tanpa filter, menyebabkan master hot wallet membuang biaya native gas (BNB/POL/TRX) lebih besar daripada nilai token yang diselamatkan (*negative yield / gas drain*). | 🔴 CRITICAL | ✅ Fixed | Diimplementasikan *Gas Simulation & Safe Gas Reserve* via `SimulateSweep` di `sweeper.go`. Saldo deposit diverifikasi terhadap ambang batas minimal per jaringan (1.0 USDT di BSC/Polygon/Solana, 2.0 USDT di TRON) serta wajib melebihi 2x cadangan keamanan gas (`safeReserve`). Transaksi debu otomatis dilewati (*dust skipped*) dengan log audit informatif `ErrDustBalance`. Dilengkapi unit test di `sweeper_test.go`. |
| **BUG-020** | Concurrency & Multi-Pod Guard | Jika backend dijalankan dalam cluster multi-pod / replica atau menerima event paralel dari 2 watcher untuk deposit address yang sama, kalkulasi `invoice.ReceivedAmount` berisiko mengalami *race condition* (overwriting balance) atau memicu duplicate payout/credit. | 🔴 CRITICAL | ✅ Fixed | Dibuat `LockManager` terdedikasi (`internal/lock/lock_manager.go`) berbasis key-mutex dan context timeout. Pada `RecordPayment`, setiap transaksi wajib mengakuisisi lock `lock:deposit:<address>`. Ditambahkan pengecekan idempotency instan terhadap `tx_hash` sebelum eksekusi state agar event ganda otomatis di-*skip* tanpa duplikasi saldo. Logika DTO dipisah ke `invoice_types.go` sehingga seluruh file tetap <= 340 baris. Dilengkapi unit test di `lock_manager_test.go` dan `invoice_service_test.go`. |
| **BUG-021** | Merchant Dashboard UX | Tabel riwayat Webhook di Merchant Dashboard belum memiliki filter status HTTP (2xx vs 4xx/5xx), pencarian berbasis Delivery ID / Order ID, maupun penampil Delivery ID unik pada inspeksi payload. | 🟡 MAJOR | ✅ Fixed | Diperbarui `WebhookLogsCard.tsx` dengan filter tab interaktif (*All*, *Success*, *Failed*), search bar instan, kolom Delivery ID, dan modal payload terdedikasi `WebhookInspectModal.tsx` yang menampilkan `X-13C-Delivery-ID` dan `Idempotency-Key` secara transparan. Seluruh komponen строго modular (<= 375 baris). |

## 3. Rencana Pengembangan Lanjutan (Future Remediation & Roadmap)

### 3.1 P1: TRON Energy Rental Integration
* **Konteks**: Biaya transfer TRC-20 USDT membutuhkan 31,895 Energy (membakar ~13-32 TRX atau ~$2.50 jika tanpa sewa energi).

* **Konteks**: Merchant saat ini login menggunakan Email + Password.
* **Rencana**: Tambahkan opsi alternatif login menggunakan tanda tangan dompet Web3 (*Sign-In with Ethereum*) via Wagmi/RainbowKit.
